# AI Product Review Intelligence Platform — Base Scaffold

This is the **foundation layer** of the platform: data model, ingestion API,
and infra wiring. Topic discovery, sentiment, keyword extraction, and the
dashboard are NOT built yet — this is the base we agreed to start with.

## What's actually working right now

- `Company -> Product -> Review` schema (PostgreSQL via SQLAlchemy async ORM)
- Alembic migrations (autogenerated + tested)
- FastAPI REST API:
  - `POST /companies`, `GET /companies`
  - `POST /companies/{id}/products`, `GET /companies/{id}/products`
  - `GET /companies/{id}/products/{id}/health` (review count, avg rating — topic/sentiment fields will populate once the pipeline exists)
  - `POST /companies/{id}/products/{id}/reviews/ingest` — bulk ingest with:
    - text cleaning (strip URLs/HTML/emoji)
    - language detection
    - **exact-duplicate rejection** via DB-level unique constraint on `(product_id, source, source_review_id)`
  - `GET /companies/{id}/products/{id}/reviews`
  - `POST /companies/{id}/products/{id}/embeddings/generate` — embeds all not-yet-embedded
    reviews (sentence-transformers) and writes vectors to Qdrant, batched so memory use stays
    flat regardless of review count. Idempotent — already-embedded reviews are skipped on rerun.
  - `POST /companies/{id}/products/{id}/topics/discover` — runs BERTopic clustering over the
    product's embedded reviews, discovers topics automatically (no predefined categories),
    and persists them. Skips (doesn't error) if there are fewer than 10 embedded reviews,
    since clustering that small a sample isn't statistically meaningful.
  - `GET /companies/{id}/products/{id}/topics` — lists discovered topics with review counts
    and positive/negative/neutral breakdowns
  - `POST /companies/{id}/products/{id}/sentiment/analyze` — aspect-based sentiment scoring.
    Splits each review into sentences, matches sentences to topics via keyword overlap, scores
    each match with VADER (lexicon-based, no LLM calls, no model downloads). A single review
    CAN end up scored against multiple topics with different sentiment each — validated against
    the spec's own example ("battery is amazing but camera is terrible" -> Battery: positive,
    Camera: negative). Also sets each review's overall sentiment. Idempotent via a
    `sentiment_computed` flag.
  - `POST /companies/{id}/products/{id}/insights/label-topics` — the first LLM-touching step
    in the whole pipeline. ONE LLM call covers ALL of a product's topics at once (not one call
    per topic, and never one call per review): turns placeholder names like
    `"battery / life / great / charge / long"` into `"Battery Life"`, plus a summary, common
    complaints/compliments, and suggestions per topic, built from a handful of representative
    review snippets rather than the full review set.
  - `POST /companies/{id}/products/{id}/insights/executive-summary` — a second, single LLM call
    per product that writes an executive summary FROM the topic-level summaries (not raw
    reviews) — requires label-topics to have run first.
  - `POST /companies/{id}/products/{id}/insights/generate` — convenience endpoint that runs
    both of the above in sequence.
  - `POST /companies/{id}/products/{id}/ask` — Ask AI, product-scoped. Answers free-form
    questions using topic-level summaries (cheap, always available) plus a semantic search
    over individual review snippets (via Qdrant, restricted to the product) for questions
    needing specific examples. Second and last LLM call site in the pipeline.
  - `POST /companies/{id}/ask` — Ask AI, company-wide. Same mechanism aggregated across all
    of a company's products — handles "compare Product A and Product B" style questions.
- Docker Compose: Postgres, Qdrant, Redis, backend — wired together
- 24 passing tests covering ingestion, dedup, embeddings, topic clustering, aspect sentiment,
  LLM insight generation, and Ask AI

All of the above was actually executed and tested before being handed to you — not just
written blind. See the "Testing caveat" note below on what could and couldn't be verified
in this sandbox specifically.

## Testing caveat: the embedding model itself is NOT verified yet

This build sandbox has network access restricted to a small allowlist (pypi, github, npm,
etc.) — **huggingface.co is not reachable**, so I could not actually download the
`sentence-transformers/all-MiniLM-L6-v2` model to confirm real embeddings generate correctly.

What I *did* verify: the pipeline logic (batching, marking reviews as embedded, writing to
Qdrant, idempotency on rerun) using a stub embedder that returns fake vectors of the correct
dimension — see `tests/test_embeddings_flow.py`. That confirms the plumbing is correct.

What still needs a check on your end, once you run this with real internet access:
```bash
cd backend
python3 -c "from app.services.embeddings import get_embedding_service; s = get_embedding_service(); print(s.encode(['test review'])[0][:5])"
```
If that prints 5 floats without error, the real model is working and you're good.

## A real bug this stage caught: qdrant-client's search() method doesn't exist anymore

Building Ask AI's semantic search surfaced an actual, load-bearing bug, not a hypothetical one:
`qdrant-client`'s `.search()` method was deprecated and then removed in newer versions — this
sandbox had 1.19.0 installed (via an earlier unpinned `pip install`), which no longer has it at
all, while `requirements.txt` was still pinned to 1.11.1. Caught immediately because a test
tried to actually retrieve real search results rather than just checking the call didn't crash.
Fixed by switching to `query_points()` (the current API) and bumping the pin to 1.19.0 to match
what was actually verified. **Worth knowing**: if this had shipped from the original pin without
ever testing semantic search for real, it likely would have broken silently later — a good
argument for pinning exact versions (already done) and not trusting a library's API surface
without a real call against it.

A related fix from the same debugging session: don't rely on catching different exception types
for "the Qdrant collection doesn't exist yet" — the in-memory test backend raises `ValueError`,
a real Qdrant server raises a different exception via HTTP 404. `search_similar` now checks
collection existence explicitly instead, which works the same way regardless of backend.

## Known limitation: Ask AI can't answer trend/time questions yet

"Why is the battery rating decreasing?" or "what are the most common complaints after the latest
update?" can't be answered precisely — there's no time-series aggregation or concept of "the
latest update" (no release-date data model exists). The LLM will do its best from whatever
review dates happen to show up in retrieved snippets, but this is NOT a real filter and
shouldn't be trusted for genuine trend analysis. That needs the dashboard's trend-analysis piece
(time-series graphs from the original spec), not built yet.

## Known limitation: aspect-matching is keyword overlap, not true semantic extraction

The sentiment stage finds aspects by checking whether a sentence literally contains one of a
topic's keywords (e.g. "battery", "charge"). It correctly catches "The battery is amazing but
the camera is terrible" because both sentences use each topic's exact vocabulary. It will
**miss** an aspect phrased without shared vocabulary — e.g. "I love how long this thing runs
without needing the wall" wouldn't be caught as a Battery aspect since it doesn't contain any
of the Battery topic's keywords. Closing that gap needs either an LLM call (against the spec's
explicit cost constraint of not calling the LLM per review) or a trained ABSA model. Flagged
here as a real, known ceiling of the traditional-ML-only approach — not silently accepted.

## Known limitation: topic stability across reruns

`topics/discover` fully recomputes clusters every time it runs and replaces the old ones —
it does NOT try to keep "Battery" as the same topic ID across runs as new reviews come in.
This is a real, unsolved problem with unsupervised clustering (flagged back at the very
start of this project) — re-clustering can shuffle cluster boundaries and IDs even when
the underlying topics are conceptually the same. Fine for a single "run once and look at
results" flow. Would need real design work (embedding-similarity matching between old and
new cluster centroids, or BERTopic's `.merge_models`) before this could support trend
analysis over time ("is the battery topic getting worse this month vs last month").

## Topic naming is currently a placeholder

Discovered topics are named from their top BERTopic/c-TF-IDF keywords, e.g.
`"battery / life / great / charge / long"` — not a clean human label like "Battery Life".
That relabeling is explicitly an LLM job (per the original spec: LLM should label
discovered topics, not discover them), which is phase 5 above, not done yet.

## Known simplifications / things flagged for later

- **Multi-tenancy**: `User` table has no company scoping yet. Fine for a single-tenant
  project/demo; would need real access control before this could serve multiple companies.
- **No Kafka yet**: the original architecture diagram had Kafka for ingestion.
  For the base we're doing direct synchronous ingestion via REST. We should introduce a
  queue (Kafka, or simpler: Redis + a task queue like Celery/RQ) once we get to the
  embedding/clustering phase, since that's the actual slow, async-worthy step.
- **Competitor comparison / scraping**: intentionally not started — real legal/ToS
  considerations for scraping Amazon/Reddit etc. (see earlier discussion). We'll use
  sample/manually-supplied data for now.
- **CORS is wide open (`*`)** — fine for local dev, must be locked down before any real deployment.

## Running it

### With Docker (full stack)

```bash
cp .env.example .env          # then edit values if needed
docker compose up --build
```

API will be at `http://localhost:8000`, interactive docs at `http://localhost:8000/docs`.

### Local dev (backend only, no Docker)

Requires Python 3.11+ and a running Postgres instance.

```bash
cd backend
pip install -r requirements.txt
cp ../.env.example ../.env    # edit DATABASE_URL to point at your local Postgres
alembic upgrade head          # create tables
uvicorn app.main:app --reload
```

### Running tests

Tests run against SQLite so they need no external services:

```bash
cd backend
DATABASE_URL="sqlite+aiosqlite:///./_test.db" pytest tests/ -v
```

### Creating a new migration after changing models

```bash
cd backend
alembic revision --autogenerate -m "describe your change"
alembic upgrade head
```
